# **缓存一致性协议**

为了提高处理器的执行速度，在处理器和内存之间增加了多级缓存来提升。但是由于引入了多级缓存，就存在缓存数据不一致问题。

对于单核CPU，通常有两种方式：

- **通写法(Write Through)**：每次cache中的内容被修改后立即写入到内存。

- **写回法(Write Back)**：cache 中内容被修改后，延迟写入内存。当cache和内存数据不一致时以cache中的数据为准。

对于多核CPU来说，cache与主存的内容同步可能会存在多线程竞争问题，又引入了以下操作：

- **写失效**：当一个CPU修改了数据，其他CPU中的该数据失效

- **写更新**：当一个CPU修改了数据，通知其他CPU对该数据进行更新

在CPU层面，提供了两种解决方案：

- **总线锁**：在多CPU情况下，某个CPU对共享变量进行操作时对总线加锁，其他CPU不能对该变量进行读写，会影响CPU性能。

- **缓存锁**：降低了锁的粒度，基于缓存一致性协议。

缓存一致性协议：当CPU写数据时，如果发现操作的变量是共享变量，即在其他CPU中也存在该变量的副本，会发出信号通知其他CPU将该变量的缓存行置为无效状态，因此当其他CPU需要读取这个变量时，发现自己缓存中缓存该变量的缓存行是无效的，那么它就会从内存重新读取。

**缓存一致性协议需要满足两种特性：**

1. 写序列化：缓存一致性协议要求总线上任意时间只能出现一个CPU写事件，多核并发的写事件会通过总线仲裁机制转换成串行化的写事件序列。

1. 写传播：一个处理器的写操作对其他处理器可见。

- - 方式一：嗅探，CPU监听总线上的所有活动。

- - 方式二：基于目录，总线事件仅发送给需要接受的CPU。

通常使用的缓存一致性协议为MESI(Modified Exclusive Shared Invalid)，实现了写回法，写失效，缓存行锁，写传播，写序列化和嗅探机制。

四种状态：

-  M: 被修改（Modified)
  当前 CPU 缓存有最新数据，其他 CPU 拥有失效数据，当前 CPU 数据与内存不一致，但以当前 CPU 数据为准。

-  E: 独享的（Exclusive)
  只有当前 CPU 有数据，其他 CPU 没有该数据，当前 CPU 数据与内存数据一致。

-  S: 共享的（Shared)
  当前 CPU 与其他 CPU 拥有相同数据，并与内存中数据一致。

-  I: 无效的（Invalid）
  当前 CPU 的缓存行无效，不能继续使用该副本。后续读取需要重新获取该缓存行，数据可能来自主存，也可能来自其他 CPU 的缓存。

处理器对缓存的请求：
- `PrRd`：CPU 读操作
- `PrWr`：CPU 写操作

总线对缓存的请求：

- `BusRd`: 窥探器请求指出其他处理器请求**读**一个缓存块
- `BusRdX`: 窥探器请求指出其他处理器请求**写**一个该处理器不拥有的缓存块
- `BusUpgr`: 窥探器请求指出其他处理器请求**写**一个该处理器拥有的缓存块
- `Flush`: 窥探器请求指出请求**回写**整个缓存到主存
- `FlushOpt`: 窥探器请求指出整个缓存块被发到总线以发送给另外一个处理器（缓存到缓存的复制）

不同状态时，执行不同操作，会产生不同的状态转移。

**当前CPU状态为Modified**

- `PrRd`：直接从缓存中读取数据，无总线事务生成，状态不变。

- `PrWr`：直接修改当前 CPU 缓存数据，无总线事务生成，状态不变。

**当前状态为Exclusive**

- `PrRd`：无总线事务生成，状态不变。

- `PrWr`：修改当前 CPU 缓存值，无总线事务生成，状态改为 M。

**当前状态为Shared**

- `PrRd`：状态不变，无总线事务生成。

- `PrWr`：发出总线事务`BusUpgr`信号，状态改为M，其他缓存看到`BusUpgr`信号时标记缓存行为Invalid。

**当前CPU状态为Invalid**

- `PrRd`： CPU 缓存不可用，需要重新获取缓存行。给总线发出`BusRd`信号，其他处理器看到`BusRd`，检查自己是否有有效的数据副本，向发送者回复 Response。

- - 如果其他缓存有有效的副本，则状态转换为Shared。

- - 如果其他缓存都没有有效的副本，则从主存读取数据，状态转换为Exclusive。

- `PrWr`：当前 CPU 缓存不可用，需要先取得缓存行所有权。给总线发出`BusRdX`信号，状态转换为 Modified。

- - 如果其他缓存有有效的副本，则从其中一个缓存中获取数据，并向缓存块中写入修改后的值。

- - 否则，从主存中获取数据。

总线操作的状态转化：

| 初始状态  | 操作             | 响应                                                  |
| --------- | ---------------- | ----------------------------------------------------- |
| Invalid   | `BusRd`          | 状态保持不变，信号忽略                                |
| Invalid   | `BusRdX/BusUpgr` | 状态保持不变，信号忽略                                |
| Exclusive | `BusRd`          | 状态变为共享 发出总线`FlushOpt`信号并发出块的内容     |
| Exclusive | `BusRdX`         | 状态变为无效 发出总线`FlushOpt`信号并发出块的内容     |
| Shared    | `BusRd`          | 状态变为共享 可能发出总线`FlushOpt`信号并发出块的内容 |
| Shared    | `BusRdX`         | 状态变为无效 可能发出总线`FlushOpt`信号并发出块的内容 |
| Modified  | `BusRd`          | 状态变为共享 发出总线`FlushOpt`信号并发出块的内容     |
| Modified  | `BusRdX`         | 状态变为无效 发出总线`FlushOpt`信号并发出块的内容     |

写操作仅在缓存行是 Modified 或 Exclusive 状态时可自由执行。如果在共享状态或无效状态，当前 CPU 需要先取得该缓存行的所有权，让其他缓存中的副本失效，这种请求所有权的广播操作称作 *Request For Ownership (RFO)*。

**MESI的问题：**

MESI 等缓存一致性协议解决的是 **coherence** 问题：同一个缓存行在多个 CPU 缓存中有副本时，所有 CPU 最终要对这个缓存行上的写入顺序达成一致。它保证的是“同一地址”的一致性，不直接保证“不同地址之间”的全局执行顺序。

在最朴素的实现里，CPU 对共享缓存行写入前，需要先发送 Invalidate 或 RFO 请求，并等待其他 CPU 确认失效。如果每次写共享数据都同步等待所有确认，流水线很容易停住，性能会很差。

为了减少这种等待，现代处理器通常会在缓存一致性协议之外加入写缓冲区和失效队列。

# 写缓冲区与失效队列

为了不让 CPU 因为等待缓存一致性消息而停下来，引入了写缓冲区和失效队列。

## 写缓冲区Store Buffer

写缓冲区是每个 CPU 私有的临时队列，用来保存尚未进入本地 cache、也尚未对其他 CPU 完全可见的写操作。

当 CPU 执行 store 指令时，如果目标缓存行不在当前 CPU 的 Modified 或 Exclusive 状态，处理器需要先通过一致性协议取得所有权。为了不让流水线一直等待，CPU 可以先把写入放进 Store Buffer，然后继续执行后续指令。一致性请求、缓存行状态转换、写入本地 cache 等动作可以在后面完成。

这样做不会破坏缓存一致性协议对“同一缓存行写入顺序一致”的要求，但会改变其他 CPU 观察到这些写入的时间点。

**存储转发Store Forwarding**

同一个 CPU 后续再读取同一地址时，会先检查自己的 Store Buffer。如果发现前面有尚未写入 cache 的 store，就直接从 Store Buffer 中取值，这叫 Store Forwarding。

例如：

```c
x = 1;   // 写入 x，可能先进入当前 CPU 的 Store Buffer，尚未对其他 CPU 可见
r1 = x;  // 当前 CPU 再读 x 时，可以通过 Store Forwarding 从 Store Buffer 读到 1
```

即使 `x = 1` 还停留在 Store Buffer 中，当前 CPU 执行 `r1 = x` 时也可以通过 Store Forwarding 读到 `1`。但是其他 CPU 此时未必能看到这个新值。

## 失效队列

失效队列也是每个 CPU 私有的队列，用来暂存其他 CPU 发来的 Invalidate 请求。

没有失效队列时，CPU 收到 Invalidate 请求后，需要立即把本地对应缓存行置为 Invalid，再回复 ACK。有了失效队列后，CPU 可以先把失效请求放入队列并回复 ACK，之后再异步处理队列中的失效请求。

这减少了写入方等待 ACK 的时间，但也带来一个窗口期：某个 CPU 已经对外回复了“我会失效这个缓存行”，但它本地还没有真正消费失效队列。在这个窗口期内，如果它继续读取该缓存行，就可能读到旧值。

## 它们带来的问题

写缓冲区和失效队列本身不是在破坏 MESI，而是在改变内存操作的**可见顺序**：

1. 本 CPU 的写入可能先进入 Store Buffer，稍后才对其他 CPU 可见。
2. 其他 CPU 的写入失效请求可能先进入 Invalidate Queue，稍后才真正让本地缓存行失效。

因此，缓存一致性协议保证的是：对同一个地址，最终所有 CPU 会看到一致的写入顺序。但程序经常关心的是多个地址之间的顺序，例如“先写数据，再写标志位”。这属于 **memory consistency / memory ordering** 问题。

典型的 Store-Load 重排序例子：

```c
// 初始状态：x = 0, y = 0

// CPU0
x = 1;   // store：写 x，可能暂存在 CPU0 的 Store Buffer 中
r1 = y;  // load：读 y，如果 CPU1 的写入尚未可见，可能读到旧值 0

// CPU1
y = 1;   // store：写 y，可能暂存在 CPU1 的 Store Buffer 中
r2 = x;  // load：读 x，如果 CPU0 的写入尚未可见，可能读到旧值 0
```

在两个 CPU 各自看来，本地执行顺序都是先 store 后 load。但如果 `x = 1` 和 `y = 1` 都暂时停留在各自的 Store Buffer 中，两个 load 都可能先从对方 cache 或内存中读到旧值，于是出现：

```text
r1 == 0 && r2 == 0  # 两个 CPU 都先读到了对方写入前的旧值
```

这不是说单线程语义真的被破坏了，而是说从其他 CPU 的视角看，store 的可见性被延后了，表现得像 load 跑到了 store 前面。

总结一下：

| 机制 | 解决的问题 | 代价或副作用 |
| --- | --- | --- |
| MESI | 同一缓存行多副本之间的一致性 | 获取写权限时可能等待其他 CPU 响应 |
| Store Buffer | 降低 store 等待一致性事务完成的开销 | 本 CPU 的写入对其他 CPU 可见可能延后 |
| Invalidate Queue | 降低处理失效请求的同步开销 | 本 CPU 可能在短窗口内继续读到旧缓存行 |
| Memory Barrier | 约束关键位置的内存操作顺序和可见性 | 会限制乱序执行和缓冲优化，成本更高 |

# 内存屏障

为了解决写缓冲区和失效队列带来的问题，引入了内存屏障。

**内存屏障**（Memory Barrier / Memory Fence）是一类用于约束内存操作顺序的机制。它可以是 CPU 指令，也可以是编译器层面的约束。

内存屏障要解决的不是“有没有缓存一致性协议”，而是“关键内存操作之间应该以什么顺序被本 CPU 执行、被其他 CPU 观察到”。

它通常有两类效果：

1. **限制重排序**：禁止特定类型的 load/store 跨过屏障重新排序。
2. **约束可见性**：要求屏障前的写入在屏障后某些操作执行前达到架构规定的可见点，或者要求屏障后的读取不能越过前面的失效处理。

注意，这里的“可见”不一定等价于“写回主存”。在写回缓存体系中，最新值可能已经进入某个 CPU 的 cache，并通过缓存一致性协议对其他 CPU 可见，但并没有真正写回 DRAM。

## 常见屏障类型

按约束的内存操作类型，可以把屏障理解为四种组合：

| 屏障类型 | 约束语义 |
| --- | --- |
| `LoadLoad` | 屏障前的 load 不能重排到屏障后的 load 之后 |
| `LoadStore` | 屏障前的 load 不能重排到屏障后的 store 之后 |
| `StoreStore` | 屏障前的 store 不能重排到屏障后的 store 之后 |
| `StoreLoad` | 屏障前的 store 不能重排到屏障后的 load 之后 |

其中 `StoreLoad` 通常最重，因为它要处理前序写入滞留在 Store Buffer 中、后续读取过早执行的问题。很多架构上的 full fence 都至少要覆盖 `StoreLoad` 语义。

从更常见的命名看，也可以分为：

| 名称 | 大致含义 |
| --- | --- |
| Load Barrier / Read Barrier | 约束读操作，常用于避免后续 load 越过前面的 load |
| Store Barrier / Write Barrier | 约束写操作，常用于保证前序 store 先于后续 store 可见 |
| Full Barrier / Full Fence | 同时约束读写，尤其覆盖 Store-Load 顺序 |

## Release / Acquire 语义

并发程序里更常见的不是直接写 CPU 屏障，而是使用语言或库提供的同步语义。例如锁、原子变量、`volatile` 等。

以发布数据为例：

```c
data = 42;  // 普通写：先发布真正的数据
ready = 1;  // 发布标志：需要 release 语义，保证 data 的写入不会落到 ready 后面
```

程序真正想表达的是：其他 CPU 如果看到了 `ready == 1`，就必须也能看到 `data = 42`。这需要在写 `ready` 前后建立 **release** 语义，禁止 `data = 42` 的可见性落到 `ready = 1` 后面。

读取方：

```c
if (ready == 1) {  // 读取发布标志：需要 acquire 语义，确认发布方的数据已经可见
    r = data;      // 普通读：必须在看到 ready == 1 之后再读取 data
}
```

读取 `ready` 后需要 **acquire** 语义，保证后续读取 `data` 不会被提前到读取 `ready` 之前，也保证能看到发布方在 release 前完成的写入。

可以粗略理解为：

| 语义 | 作用 |
| --- | --- |
| Release | 前面的普通读写不能重排到 release 写之后 |
| Acquire | 后面的普通读写不能重排到 acquire 读之前 |
| Full Fence | 同时限制屏障前后的读写重排 |

## Java 中的内存屏障

Java 程序员通常不直接写内存屏障，而是通过 Java 内存模型提供的同步原语间接获得屏障效果。

`volatile` 的典型语义：

1. 对 `volatile` 变量的写具有 release 语义：写之前的普通读写不能重排到 volatile 写之后。
2. 对 `volatile` 变量的读具有 acquire 语义：读之后的普通读写不能重排到 volatile 读之前。
3. 对同一个 `volatile` 变量的写与读之间建立 happens-before 关系。

常见的保守插屏障策略可以这样理解：

| 操作 | 典型屏障效果 |
| --- | --- |
| volatile 写前 | `StoreStore`，保证前面的普通写先于 volatile 写可见 |
| volatile 写后 | `StoreLoad`，防止后续读写越过 volatile 写 |
| volatile 读后 | `LoadLoad` + `LoadStore`，防止后续读写越过 volatile 读 |

不同 CPU 架构内存模型不同，JVM 实际生成的机器指令也不同。比如 x86 的内存模型相对较强，很多 LoadLoad、LoadStore、StoreStore 语义天然满足；但 StoreLoad 仍然需要更强的序列化手段。ARM、POWER 等弱内存模型通常需要更显式的屏障指令。

## 总结

1. 缓存一致性协议解决的是同一缓存行多副本之间的一致性问题。
2. MESI 能保证同一地址的写传播和写序列化，但不等于保证所有内存操作按程序顺序被所有 CPU 观察到。
3. Store Buffer 和 Invalidate Queue 是性能优化，它们让写入和失效处理异步化，也让其他 CPU 观察到内存操作的顺序可能不同于本 CPU 的程序顺序。
4. 内存屏障用于在关键位置恢复必要的顺序约束和可见性约束。
5. 高级语言通常不会让程序员直接操作硬件屏障，而是通过锁、原子变量、`volatile` 等同步原语映射到合适的编译器约束和 CPU 屏障。
