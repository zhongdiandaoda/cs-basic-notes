# 大语言模型 Introduction

大语言模型（Large Language Model，LLM）是以海量文本、代码和多模态数据训练得到的生成式模型。它的基本任务并不神秘：给定已有上下文，预测下一个最可能出现的 token。通过把这个简单任务扩展到足够大的数据、参数规模和训练计算量，模型学习到了语言结构、事实关联、代码模式与部分推理能力。

对研发工程师而言，理解 LLM 的重点不是把它看成“会聊天的搜索引擎”，而是理解它作为一个**条件概率模型**如何被训练、如何在推理时逐 token 生成，以及为什么模型能力、上下文、工具和外部知识要由不同的工程组件共同承担。

## 一句话理解

给定前面的 token 序列，语言模型会为“下一个 token 可能是什么”计算一个概率分布。换句话说，它会根据已经出现的内容，判断接下来最可能出现哪些字、词片段或符号。

生成一段文本就是重复执行以下过程：

1. 将输入文本编码为 token。
2. 模型计算下一个 token 的概率分布。
3. 按贪心、采样或受约束解码选出一个 token。
4. 将该 token 追加到上下文，继续预测下一个 token。
5. 直到生成结束标记、达到长度限制，或被外部系统停止。

模型不会直接“检索一条答案”；它是在当前上下文约束下，为下一个 token 分配概率。因此，提示词、历史对话、检索结果、工具调用结果都会改变后续生成的概率分布。

## LLM 不等于聊天机器人

“聊天机器人”是最常见的交互形态，但不是 LLM 的本体。可以将一个完整 AI 系统拆成下面几层：

| 层次   | 主要职责             | 典型内容                          |
| ---- | ---------------- | ----------------------------- |
| 基座模型 | 根据上下文生成或评分 token | Transformer、模型权重、Tokenizer    |
| 推理服务 | 高效执行模型并管理请求      | 批处理、KV Cache、并行策略、限流          |
| 对齐层  | 约束输出风格、帮助性和安全边界  | System Prompt、SFT、偏好优化、安全策略   |
| 知识层  | 提供时效或私有事实        | RAG、搜索、数据库、企业知识库              |
| 工具层  | 让模型读取状态或执行动作     | Function Calling、MCP、API、代码执行 |
| 应用层  | 将能力封装成用户可完成的任务   | 问答、代码助手、客服、Agent              |

因此，模型能力不足不一定要靠“换更大模型”解决：

- 缺少最新或私有事实时，通常需要检索、数据库或工具。
- 需要确定性计算、写操作或访问业务系统时，通常需要工具调用。
- 需要稳定地完成多步骤任务时，通常需要工作流、状态管理和评测。
- 需要降低幻觉、保证格式或安全时，通常需要约束、验证和回退策略。

## 从文本到 Token

模型处理的基本单位不是自然语言中的“词”，而是 token。Tokenizer 将输入文本拆分成可被模型索引的整数序列；常见 token 可能是一个字、词的一部分、一个空格或标点。

```text
用户文本
  -> Tokenizer
  -> token IDs
  -> Embedding 向量
  -> Transformer
  -> 下一个 token 的概率分布
  -> 解码策略
  -> 输出文本
```

token 直接决定了三个工程约束：

| 概念 | 含义 | 工程影响 |
|---|---|---|
| 上下文窗口 | 单次请求可处理的 token 上限 | 限制输入文档、历史对话和输出长度的总和 |
| 输入 token | Prompt、上下文、检索内容等消耗的 token | 影响成本、首 token 延迟和注意力计算量 |
| 输出 token | 模型生成的 token | 影响生成时延、成本和流式体验 |

不同模型的 tokenizer 不同，字符数不能准确等价为 token 数。实际集成时，应使用目标模型的 tokenizer 或平台提供的计数接口估算预算。

## 为什么 Transformer 成为主流架构

现代 LLM 大多以 Transformer 为基础。其核心是自注意力机制（self-attention）：序列中每个 token 可以根据任务需要，动态关注上下文中的其他 token。

对一个 token 来说，注意力计算可以理解为三个连续动作：

1. 当前 token 提出查询（Query）：它需要从上下文中寻找什么信息。
2. 当前 token 与历史 token 的索引（Key）进行匹配：哪些位置与当前任务最相关。
3. 按相关性权重汇聚这些位置的内容（Value）：将最有用的信息带到当前位置。

多头注意力（Multi-Head Attention）让模型从多个子空间同时建立关联，例如一个头关注语法关系，另一个头关注实体指代或代码中的变量依赖。注意力层之后通常还有前馈网络、残差连接和归一化层，它们共同构成 Transformer Block。

### Decoder-only 与因果掩码

通用生成式 LLM 多使用 Decoder-only 架构。它在训练和推理中采用因果掩码（causal mask）：当前位置只能关注自己及之前的位置，不能看到后续 token。

```text
已知上下文:  x1  x2  x3  x4
预测目标:                    x5

x4 可以关注 x1..x4
x5 生成后，才能作为后续位置的上下文
```

这个约束使训练目标和生成过程一致，也解释了 LLM 为什么天然适合续写、对话、代码补全和结构化生成。

## 训练流程

一个可用的通用模型通常经历多个阶段。不同模型的具体配方不同，但阶段划分具有普遍性。

| 阶段 | 目标 | 训练数据与产物 |
|---|---|---|
| 数据准备 | 构建质量可控、覆盖足够广的数据集 | 清洗、去重、质量过滤、格式规范化、数据配比 |
| 预训练 | 学习语言与通用模式 | 大规模文本、代码、数学和多模态语料；得到基座模型 |
| 监督微调（SFT） | 学会遵循指令和任务格式 | 指令-回答样本、领域任务样本 |
| 偏好优化 | 优化有用性、风格和安全性 | 人类或模型偏好数据、奖励模型或直接偏好目标 |
| 领域适配 | 提升特定场景表现 | 行业语料、业务任务、参数高效微调或继续训练 |
| 评测与发布 | 验证能力、风险与回归 | 基准集、业务集、红队集、线上观测 |

### 预训练

预训练通常是下一 token 预测。模型读取大量 token 序列，以交叉熵损失衡量预测分布与真实下一个 token 的差异，并通过反向传播更新参数。

预训练赋予模型广泛的语言和模式能力，但它并不保证：

- 掌握训练截止日期之后的新知识。
- 对每个事实都准确。
- 自动遵循用户指令。
- 自动满足业务格式、权限和安全要求。

### 后训练与对齐

后训练的目标是让基座模型从“擅长续写”变成“擅长协助完成任务”。SFT 先让模型学习指令格式和示例行为；偏好优化再根据回答质量、帮助性、安全性等偏好，调整模型更倾向输出什么。

这也是同一基座模型在不同产品中体验差异显著的原因之一：差异不仅来自模型规模，也来自后训练数据、系统提示词、工具编排和产品侧约束。

## 推理：模型如何生成回答

推理阶段不再更新参数，而是执行前向计算并逐 token 生成。一次请求可以拆成两个阶段：

| 阶段 | 处理内容 | 典型瓶颈 |
|---|---|---|
| Prefill | 处理完整输入上下文，建立初始 KV Cache | 输入长度、注意力计算、首 token 延迟 |
| Decode | 每次生成一个新 token，并复用历史 KV Cache | 输出长度、显存带宽、每 token 延迟 |

KV Cache 缓存了历史 token 在注意力层中的 Key 和 Value，避免每生成一个 token 都重新计算全部历史上下文。它是长上下文推理和多轮会话的重要性能基础，但也会占用大量显存。

### 解码策略

模型输出的是概率分布，解码策略决定如何从中选取 token。

| 策略 | 特点 | 适用场景 |
|---|---|---|
| 贪心解码 | 每次选择概率最高的 token，结果稳定但容易保守 | 分类、固定格式、低创造性任务 |
| Temperature | 调整分布平滑程度；越高越随机 | 需要控制创造性和稳定性的通用生成 |
| Top-k | 仅在概率最高的 k 个 token 中采样 | 控制长尾噪声 |
| Top-p | 在累计概率达到 p 的候选集合中采样 | 开放式文本生成 |
| 受约束解码 | 只允许符合语法或 schema 的 token 路径 | JSON、SQL、函数参数、结构化输出 |

Temperature、Top-k 与 Top-p 不能弥补事实缺失或推理错误。它们影响的是输出分布的随机性，而不是模型是否真正具备对应知识。

## 上下文、记忆与知识

模型参数中编码的是训练期间获得的统计规律；一次请求中可见的信息则位于上下文窗口。二者需要明确区分。

| 信息来源 | 变化速度 | 是否可追溯 | 常见实现 |
|---|---|---|---|
| 模型参数 | 慢，需要训练或微调 | 通常不可直接定位来源 | 预训练、微调 |
| Prompt 上下文 | 快，随请求变化 | 可保留输入来源 | System Prompt、历史对话、Few-shot 示例 |
| 外部知识 | 快，可更新 | 可以给出引用与权限控制 | RAG、搜索、数据库 |
| 长期记忆 | 中等，需要治理 | 应保存来源、时间和置信度 | 用户画像、摘要、向量库、状态存储 |

RAG（Retrieval-Augmented Generation）并不是把资料“塞进模型”，而是在回答前检索候选材料，将相关片段放入上下文，再由模型基于这些材料组织答案。它适合解决知识更新、私有文档、可追溯引用等问题；但检索质量、切分策略、召回范围和上下文预算都会直接影响最终效果。

## 幻觉与可靠性边界

LLM 的优化目标是生成与上下文匹配的高概率 token 序列，不是保证每一个陈述都为真。当输入证据不足、问题超出训练或上下文覆盖范围、提示中存在误导信息时，模型可能生成流畅但不正确的内容，这通常被称为幻觉（hallucination）。

降低幻觉应采用分层策略：

1. 对时效事实、业务数据和权限信息，优先使用受控检索或工具查询。
2. 将检索证据与最终结论绑定，要求引用来源或返回证据片段。
3. 让模型输出可验证的结构化结果，再由程序校验字段、范围和 schema。
4. 对高风险动作使用规则、权限校验、人工确认和可回滚机制。
5. 建立离线评测集与线上观测，持续识别错误模式，而不是只依赖主观试用。

## 从 LLM 到 Agent

LLM 可以决定“下一步应该说什么”，但 Agent 还需要能观察环境、调用工具、维护状态、执行动作并验证结果。一个典型 Agent 循环可以表示为：

```text
目标与约束
  -> 读取当前上下文和外部状态
  -> LLM 规划或选择下一步
  -> 调用工具
  -> 获得工具结果
  -> 校验结果，更新状态
  -> 完成、重试或进入下一轮
```

在这个循环中，LLM 是概率性的决策组件，而工具、状态机、权限系统、验证器和观测系统负责将其纳入可控的工程系统。对于需要修改数据、调用生产 API 或执行长程任务的场景，后者往往比单纯更换模型更关键。

## 学习路径

建议以“数据如何流动”为主线学习 LLM，而不是孤立记忆概念：

1. **输入与表示**：Tokenizer、Embedding、位置编码、上下文窗口。
2. **模型结构**：Attention、Transformer Block、Decoder-only、MoE。
3. **训练**：预训练、SFT、偏好优化、强化学习、数据工程。
4. **推理系统**：Prefill、Decode、KV Cache、批处理、量化和并行。
5. **应用工程**：Prompt、RAG、Tool Calling、结构化输出、Agent。
6. **质量与安全**：离线评测、线上观测、权限、注入防护、人工兜底。
